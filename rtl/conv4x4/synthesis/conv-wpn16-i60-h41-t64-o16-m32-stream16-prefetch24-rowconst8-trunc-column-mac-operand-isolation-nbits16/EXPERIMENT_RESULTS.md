# WPN16 m32 MAC operand-isolation experiment

## Question and implementation

Test whether zeroing both operands of every MAC outside `HADAMARD` reduces
active-job power. `HADAMARD` is the only state in which the registered product
bank captures `w_hadamard_product_current`. The FSM, arithmetic, capture edge,
and original core are otherwise unchanged. The experiment uses the canonical
WPN16 16-bit workload and 32 MACs.

The candidate RTL SHA-256 is
`08a6d31d7bcc56586b3ae6fc2b3e11bb0b028ac843d7502627f3622271768f78`;
the unchanged baseline RTL SHA-256 is
`b00f42d3b78ebcc81535c173aba35698db3a54019b06449884ff4a57ebea1059`.
The experimental RTL and flow configuration were published at commit
`8fe95dde733adb950748634d141a057d03ab273b` before the remote run.

## Functional and timing results

- Verilator, canonical `sim-032-3-3-normal-trunc-nbits16`: PASS; 8,100 valid
  writes, 576 inverse tiles, 5,387 active job cycles.
- Xcelium gate-level with SDF: PASS; 8,100 valid writes, zero golden
  mismatches, 5,387 cycles (10.774 us) from accepted `p_start` to `p_end`.
- SDF annotation reported zero errors and 5,546 warnings. The warnings remain
  in the run log and should not be hidden; the simulation completed normally.
- Genus timing met the configured constraints: 10 ps at the slow setup corner
  and 224 ps at the typical corner. The critical path remains the output
  boundary path from `r_output_write_count_reg` to `p_output_data_write[63]`,
  not a path through a MAC.
- Candidate mapped area was 36,787.338 um2 cell area plus 14,745.654 um2 net
  area (51,532.992 um2 total). The matched baseline was 50,771.518 um2 total,
  so candidate total area increased by 761.474 um2 (+1.50%). Cell count rose
  from 29,049 to 29,827 (+2.68%).

## Matched active-job power

Both runs use TSMC 28 nm TT, 0.90 V / 25 C, PLE, the same routed-SDF
simulation method, and the accepted-job interval 101 ns to 10,875 ns. Values
are Joules estimates, not measurements on silicon or an FPGA board.

| Power category (mW) | Baseline | MAC operands isolated | Delta |
| --- | ---: | ---: | ---: |
| Register dynamic | 2.98128 | 2.68904 | -0.29224 |
| Logic dynamic | 6.30149 | 8.32220 | +2.02071 |
| Clock dynamic | 0.19743 | 0.19937 | +0.00194 |
| **Total dynamic** | **9.48020** | **11.21060** | **+1.73040 (+18.25%)** |
| Leakage | 0.161098 | 0.155578 | -0.005520 |
| **Total active-window power** | **9.64130** | **11.36620** | **+1.72490 (+17.89%)** |

The aggregate dynamic power of all 32 `MAC_LANES[].multip` instances rose from
2.800912 mW to 4.308976 mW (+1.508064 mW, +53.84%). The register category
fell, but the logic category—particularly the MAC hierarchy—rose much more.
The measurements show that this implementation of operand isolation is
counterproductive for this design; they do not prove that every possible
isolation strategy will increase power.

## Conclusion

Do not promote this variant as a power optimization. Keep the unisolated WPN16
m32 as the reference. The next useful direction, if exploring further, is to
avoid placing a wide zero-select mux on both operands of every multiplier and
instead investigate a lower-overhead enable/gating structure with the same
capture-cycle correctness checks. That would be a new experiment, not a
correction to this result.
